## 1. 別環境で再開する手順

```bash
git clone https://github.com/SalsNoah/mj_study.git
cd mj_study
npm install
npm run dev
```

- Node 20 以上。開発サーバーは `vite --host`、既定ポート **5174**（`vite.config.ts`）。
- 秘密情報・`.env`・サーバーはない。問題データはブラウザの localStorage のみ。
- 学習データを持っていく場合は、元端末の設定から JSON バックアップを書き出し、先方の設定で復元する。
- `samples-local/` は gitignore。精度検証用スクショと学習スクリプトは Git に無い。必要なときは手元からコピーする。
- 公開サイトを触ってもコードは変わらない。サイト更新は `main` への push のみ（GitHub Actions → Pages）。

2026-10-04 時点で origin/main の先頭は `adaed85`（スマホ向け点数読み・供託・本場）。別環境はこのコミットから始めればよい。

## 2. アプリの立ち位置

スマホ優先の個人用麻雀学習帳（PWA）。ログインなし、サーバー保存なし。牌姿・解説・メモ・学習履歴を localStorage に置き、検索・クイズ・URL 共有する。

| 項目 | 内容 |
|---|---|
| スタック | React 19、Vite 6、TypeScript strict、HashRouter、Vitest、Playwright |
| エイリアス | `@` → `src/` |
| `base` | `./`（GitHub Pages のサブパスでも相対パスで動かす） |
| 牌の描画 | 外部牌画像は使わない。`TileFace` 等が SVG／Canvas で描く |
| 共有 | `#share=v1.<payload>`。HashRouter の `#/path` と衝突しないよう `App.tsx` で先に判定する |

下部ナビ：作成 `/`、学習帳 `/library`、テスト `/test`、記録帳 `/records`、設定 `/settings`。  
スクショ取り込みはナビに出さず、作成画面から `#/import`。

## 4. 保存キー（端末・ブラウザ単位）

| キー | 中身 | バックアップ JSON に含むか |
|---|---|---|
| `mahjong-study:v1` | 問題・タグ・学習・設定（`schemaVersion: 1`） | 含む |
| `mahjong-study:theme` | `normal` / `cool` / `cute` | **含まない**（端末の見た目） |
| `mahjong-study:import:v2` | 確認画面で直した牌の追加見本 | 含まない |
| `mahjong-study:import-draft` | 取り込み → 作成への一時データ（sessionStorage） | 含まない |

容量目安：警告 3MiB、上限 4MiB。壊れたデータは自動初期化しない。設定の全削除だけが空にする手段。

テーマは `src/app/theme.ts`。CSS 変数は `[data-theme]`。キュート時だけ Zen Maru Gothic を遅延読み込み。`index.html` の起動スクリプトも同じキーを読む。

## 5. スクショ取り込み（現行の中心）

ゼロ設定。範囲指定なし。作成画面で画像を選ぶ → `#/import` で自動読み → 確認 → 作成へ下書き。

処理の入口は `autoRead()`（`src/features/import/autoRead.ts`）。

### 5.1 ファイル分担

| ファイル | 役割 |
|---|---|
| `auto.ts` | 手牌・鳴き・雀魂パネル・ドラ・供託段の位置 |
| `imageTools.ts` | 切り出し、回転、牌／文字の特徴量、数字の分割候補 |
| `templates.ts` | 見本バンクとの一致（コサイン類似） |
| `parse.ts` | 局・風・点数パース、合計からの推定、理牌 DP、副露の組み立て |
| `autoRead.ts` | 全体の読み取り、雀魂パネル OCR、モデル読込 |
| `ImportPage.tsx` | 確認 UI。直した牌は `rememberTile` で端末に覚える |
| `draft.ts` | 作成画面との受け渡し |

同梱モデルは `public/import-model.json`。`MODEL_VERSION`（現在 **4**）をクエリ `?v=` に付けて古いキャッシュと混ぜない。見本の切り出し方を変えたら **バージョンを上げる**。

牌特徴：12×16 RGB＋赤／緑マップ。文字特徴：16×24。

### 5.2 ゲーム判定と手牌

1. 白〜クリーム色の低彩度塊から手牌帯を探す（`locateHand`）。
2. 各牌を雀魂／天鳳の見本に当て、平均一致が高い方をゲームとする。手牌平均が `HAND_OK`（0.5）未満、または枚数が異常なら失敗。
3. 門前は理牌されている前提。枚数が 3 で割って 2 余るときは右端をツモとみなし、それ以外に `sortedLabels`（並び制約つき DP）を使う。
4. 副露は回転牌を手がかりに組む。組として成り立たないものは `sure: false` にして確認させる。

### 5.3 雀魂の中央パネル（現行パス）

天鳳はまだ `centerRegions` の相対位置＋明るい文字読み。雀魂は灰色の八角形パネルを切り、正方形に直し、席ごとに 0/90/180/270 度回して同じ座標を読む。

正方形化したパネル（自分を下）での相対箱：

- 点数：`(0.3, 0.635, 0.4, 0.125)`
- 風の札：`(0.02, 0.73, 0.2, 0.22)`（その家から見て左下）
- 局：`(0.33, 0.34, 0.34, 0.15)`
- 余白 `PANEL_MARGIN = 0.12`

拡大は二系統。数字の隙間を残す nearest（`resample`）と、漢字がつぶれない bilinear（`resampleSmooth`）。

風の並び：赤い札が東。自分の札から **反時計回り** に東→南→西→北。三麻は北がなく対面が空く。`decodeSeatWind` は文字一致と赤画素を組み合わせ、次点との差が小さいときは自風を空にする。

点数は接した数字の等分割候補をいくつか試し、妥当な点数として読める分割を選ぶ。合計（4 人 100000 / 3 人 105000、供託×1000 を除く）に合うよう、最大 2 桁まで次点ラベルへ置換（`checkByTotal`）。それでも欠ける席は `estimateScores`。供託が読めないときは不足が 0〜5000 かつ 1000 の倍数なら許容。

供託・本場はドラ表示の下の段（`locateCounterRow`）。数字見本は点数用の `0`〜`9` と混ぜないため **`k0`〜`k9`**。相対 x は供託 0.31–0.47、本場 0.79–0.97。一致 0.6 未満は読まない。

三麻判定：対面点数が null かつ対面位置の十分な高さの文字が 2 個未満。

### 5.4 確認画面から作成へ

`sure` が低い牌と `?` は利用者が直す。確定後、手牌・鳴き・ドラ・局・本場・供託・自風・巡目・点数を下書きする。推定した点数は注記を付ける。

## 7. 公開とキャッシュ

`.github/workflows/pages.yml`：`main` push で `npm ci` → `npm run build` → Pages。

フロントの見た目が古いときは Service Worker の stale が多い。

- `public/sw.js` の `CACHE`（現在 `mahjong-study-v18`）を **リリースのたびに上げる**。
- モデルを変えたら `MODEL_VERSION` も上げる。
- 開発中に Vite が落ちると SW が古い JS／JSON を返すことがある。ポートを占有したままの古い Vite を止めてから `npm run dev` し直す。

`npm run build` は `tsc --noEmit` 付き。公開前に通す。

## 9. 既知の限界と次にやるとよいこと

精度は「確認画面で直せる」前提。完全自動ではない。

- **天鳳**の左右点数は回転して読む方式にしていない。読めない席は合計推定に倒れやすい。
- 雀魂でも **s12 / s14 の leave-one-out** では 5/6/8/3 の取り違えが残ることがある。フルモデル＋合計照合では確認画面まで通ることが多い。
- **s01 の供託**はアイコンと数字がくっついて 0 本と誤読することがある。本場は読めることが多い。
- 三麻の巡目で 0 を 1 と読む例があった。
- `src/domain/search.test.ts` の A44 付近がタイムアウト気味で稀に落ちる。取り込みとは無関係。

着手候補（優先は利用者が決める）：

1. 天鳳の点数も雀魂と同じ「席ごとに回して読む」
2. 供託アイコンと数字の分離
3. スマホ解像度の見本を `import-model.json` に足す（`MODEL_VERSION` と SW を上げる）

## 10. 変更時の約束

- 製品データはサーバーに送らない。解析・外部牌画像・無断の IndexedDB 化はしない。
- バックアップ対象とテーマ／取り込み見本を混ぜない。
- 読み取りの切り出しやラベル体系を変えたら `MODEL_VERSION` を上げ、可能なら `import.test.ts` にケースを足す。
- 見た目を変えたリリースでは `public/sw.js` のキャッシュ名を上げる。
- `samples-local/` と個人スクショはコミットしない。
- UI を変えたら実機またはブラウザで操作確認する（見た目のスクリーンショットだけでは足りない）。
- `main` 直 push で Pages が更新される。デプロイ待ちの watch は依頼があるときだけ。

## 11. 打牌別の受け入れ追加候補（2026-10-04）

作成・詳細・テスト回答後に受け入れ表示を追加。計算は `src/domain/ukeire.ts`、表示は `src/components/UkeirePanel.tsx`。追加した範囲・定義は [受け入れ設計](受け入れ設計.md)、結果と未検証範囲は [受け入れ検証](受け入れ検証.md) を読む。保存schema、正解判定、共有形式は変更していない。公開状態は対応するPRとActionsで確認する。

追加の明示依頼により、34種の残枚数を自動上限以内で手動調整する候補を追加した。調整は解析画面内のみで、局面変更・別問題・画面移動では自動へ戻る。[残枚数調整設計](残枚数調整設計.md) と [残枚数調整検証](残枚数調整検証.md) を参照する。初期版のシャンテン計算本体と保存schemaは変更しない。

手牌・鳴き・ドラ表示牌の合計で同種5枚目を入力段階から防止し、OCR修正にも同じ上限を適用する。[入力上限修正](牌枚数上限修正.md) に修正と検証範囲を記載する。
